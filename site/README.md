# Nidhogg — website

Static frontend that displays Nidhogg's results (analyzed PyPI packages,
their URL findings, bundled native binaries, and aggregate charts). No
build step: plain HTML/CSS/JS, no dependencies, no npm/node.

Three tabs, all scoped to the day picked in the day selector: **Urls**
(one row per URL finding), **Binaries** (one row per detected native
binary, grouped by package), and **Charts** (day-aggregate bar charts:
threat breakdown, suspicious-vs-clean, binary format, binary signature).

## Structure

```
site/
├── index.html      # page structure (3 tabs: Urls / Binaries / Charts)
├── style.css        # theme (dark/light via prefers-color-scheme)
├── app.js            # fetches data/index.json + data/<day>.json, renders all 3 tabs
└── data/
    ├── index.json     # available dates (generated by the workflow)
    ├── trends.json    # cross-day rollup: daily totals, top domains, repeat offenders (generated by the workflow)
    └── YYYY-MM-DD.json  # one file per day (generated by the workflow)
```

## Running locally

`app.js`'s `fetch()` needs to be served over HTTP — double-clicking
`index.html` (`file://`) makes the browser block the request via CORS.

```bash
cd site
python3 -m http.server 8000
```

Open <http://localhost:8000> in the browser. Ctrl+C to stop.

Any static server works the same, for example:

```bash
npx serve site      # if you have Node
# or
uv run python -m http.server 8000 --directory site
```

## Data

`app.js` fetches `data/index.json` to know which dates are available,
populates the day selector with that, and loads `index.json.latest` by
default. Changing the selector fetches `data/<date>.json` and re-renders
stats/spine/table scoped to that day.

`site/data/*.json` is generated output (`.gitignore`d, not committed) —
regenerated by `scripts/build_site_data.py` from `history/*.jsonl` on every
pipeline run, and by the GitHub Actions workflow before each deploy. To try
the page locally without running the real pipeline, hand-write your own
`data/YYYY-MM-DD.json` + `data/index.json` following the schema below (e.g.
a small sample dataset), or point `--history-dir`/`--site-data-dir` at a
real `history/` directory and run the script.

`data/index.json`:

```json
{
  "generated_at": "2026-07-15T12:00:00Z",
  "latest": "2026-07-15",
  "dates": ["2026-07-15", "2026-07-14", "..."]
}
```

`data/2026-07-15.json` (same shape for any `YYYY-MM-DD.json`):

```json
{
  "generated_at": "2026-07-15T12:00:00Z",
  "stats": { "total_packages": 1245, "malicious": 4, "clean": 1241 },
  "packages": [
    {
      "name": "some-pkg",
      "version": "1.2.3",
      "download_url": "https://files.pythonhosted.org/packages/.../some-pkg-1.2.3.tar.gz",
      "analyzed_at": "2026-07-15T11:58:03Z",
      "total_findings": 1,
      "findings": [
        {
          "url": "http://evil.example/payload",
          "file": "setup.py",
          "line": 42,
          "layer": "ast",
          "method": "base64",
          "domain_threat": "exfiltration",
          "http_status": 200,
          "http_title": "Index of /",
          "cert_issuer": "Let's Encrypt"
        }
      ]
    }
  ],
  "binaries": [
    {
      "package": "some-pkg",
      "analyzed_at": "2026-07-15T11:58:03Z",
      "binaries": [
        {
          "name": "helper.dll",
          "file": "some_pkg/native/helper.dll",
          "sha256": "b502cb4c5b46b8d4192ec6bcb600ce8922f1afc396fcf646e8765c6eba74a0bf",
          "format": "pe",
          "signed": true,
          "signer": "CN=Example Corp"
        }
      ]
    }
  ]
}
```

`data/trends.json` (cross-day, not scoped to any single date):

```json
{
  "generated_at": "2026-07-20T12:00:00Z",
  "daily": [
    {"date": "2026-07-15", "total_packages": 120, "malicious_packages": 2, "total_findings": 5}
  ],
  "top_domains": [
    {"domain": "evil.example", "count": 14, "threat": "exfiltration"}
  ],
  "repeat_offenders": [
    {"name": "some-pkg", "days_seen": 3, "total_findings": 9, "first_seen": "2026-07-10", "last_seen": "2026-07-18"}
  ]
}
```

`daily` covers every day with history, oldest first. `top_domains` is
capped at 10 and counts only findings with a non-null `domain_threat`
(threat-tagged), so common benign domains never crowd it out. `repeat_offenders`
lists packages malicious on 2+ distinct days; `first_seen`/`last_seen` bound
the malicious occurrences specifically (not just any day the package was
analyzed), while `total_findings` is the package's lifetime finding count
across every analyzed day, malicious or not.

`binaries` is populated only when the analysis ran with `--check-binaries`
(see the root [`README.md`](../README.md#binary-scanning---check-binaries));
otherwise it's an empty list — never omitted, so `app.js` doesn't need to
special-case its absence. `format` is always one of the raw lowercase
values `pe`/`macho`/`elf`/`unknown` (the Binaries and Charts tabs relabel
them for display); `signed` is `true`/`false`/`null` (`null` when the file
couldn't be parsed at all); `signer` is the certificate subject, `"ad-hoc"`
for an unsigned-but-ad-hoc-signed Mach-O binary, or `null`.

`version` and `download_url` are `null` for packages analyzed through the
batch `analyze` flow (no version concept there) and set for packages
discovered via `fetch`/`monitor`; `download_url` feeds the inline PyPI and
inspector.pypi.io links in the package cell.

The three enrichment fields are **optional** per finding: `http_status`
(int) and `http_title` (string) are filled in by `--check-http`;
`cert_issuer` (string) is filled in by `--check-ssl`. Any of them can be
`null` (checked, no result) or missing entirely (flag not used). The page
shows them inline under the URL: a status badge colored by class (2xx
green / 3xx amber / 4xx-5xx red), the title in italics, and the
certificate issuer (`LE` if it's Let's Encrypt).

To try other data, just add/edit `data/YYYY-MM-DD.json` files (and their
dates in `data/index.json`) following this schema and reload the page (no
need to restart the server).

In production these files aren't edited by hand: they're generated by a
script (`scripts/build_site_data.py`, turning one
`history/YYYY-MM-DD.jsonl` into one `site/data/YYYY-MM-DD.json`, plus an
`index.json` with the available dates) as part of the GitHub Actions
workflow. See
[`docs/deployment-github-actions-pages.md`](../docs/deployment-github-actions-pages.md)
for the full design of that part — this README only covers running and
trying out the site locally.
