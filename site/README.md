# Nidhogg — website

Static frontend that displays Nidhogg's results (analyzed PyPI packages
and their URL findings). No build step: plain HTML/CSS/JS, no
dependencies, no npm/node.

## Structure

```
site/
├── index.html      # page structure
├── style.css        # theme (dark/light via prefers-color-scheme)
├── app.js            # fetches data/index.json + data/<day>.json, renders the table
└── data/
    ├── index.json     # available dates (generated by the workflow)
    └── YYYY-MM-DD.json  # one file per day (generated by the workflow)
```

## Running locally

`app.js`'s `fetch()` needs to be served over HTTP — double-clicking
`index.html` (`file://`) makes the browser block the request via CORS.

```bash
cd site
python3 -m http.server 8000
```

Open <http://localhost:8000> in the browser. Ctrl+C to stop.

Any static server works the same, for example:

```bash
npx serve site      # if you have Node
# or
uv run python -m http.server 8000 --directory site
```

## Data

`app.js` fetches `data/index.json` to know which dates are available,
populates the day selector with that, and loads `index.json.latest` by
default. Changing the selector fetches `data/<date>.json` and re-renders
stats/spine/table scoped to that day.

The `site/data/*.json` checked into the repo is a **sample dataset** (7
days, 10 mock packages, 4 malicious) so the page can be tried and
designed without depending on the real pipeline.

`data/index.json`:

```json
{
  "generated_at": "2026-07-15T12:00:00Z",
  "latest": "2026-07-15",
  "dates": ["2026-07-15", "2026-07-14", "..."]
}
```

`data/2026-07-15.json` (same shape for any `YYYY-MM-DD.json`):

```json
{
  "generated_at": "2026-07-15T12:00:00Z",
  "stats": { "total_packages": 1245, "malicious": 4, "clean": 1241 },
  "packages": [
    {
      "name": "some-pkg",
      "version": "1.2.3",
      "download_url": "https://files.pythonhosted.org/packages/.../some-pkg-1.2.3.tar.gz",
      "analyzed_at": "2026-07-15T11:58:03Z",
      "total_findings": 1,
      "findings": [
        {
          "url": "http://evil.example/payload",
          "file": "setup.py",
          "line": 42,
          "layer": "ast",
          "method": "base64",
          "domain_threat": "exfiltration",
          "http_status": 200,
          "http_title": "Index of /",
          "cert_issuer": "Let's Encrypt"
        }
      ]
    }
  ]
}
```

`version` and `download_url` are `null` for packages analyzed through the
batch `analyze` flow (no version concept there) and set for packages
discovered via `fetch`/`monitor`; `download_url` feeds the inline PyPI and
inspector.pypi.io links in the package cell.

The three enrichment fields are **optional** per finding: `http_status`
(int) and `http_title` (string) are filled in by `--check-http`;
`cert_issuer` (string) is filled in by `--check-ssl`. Any of them can be
`null` (checked, no result) or missing entirely (flag not used). The page
shows them inline under the URL: a status badge colored by class (2xx
green / 3xx amber / 4xx-5xx red), the title in italics, and the
certificate issuer (`LE` if it's Let's Encrypt).

To try other data, just add/edit `data/YYYY-MM-DD.json` files (and their
dates in `data/index.json`) following this schema and reload the page (no
need to restart the server).

In production these files aren't edited by hand: they're generated by a
script (`scripts/build_site_data.py`, turning one
`history/YYYY-MM-DD.jsonl` into one `site/data/YYYY-MM-DD.json`, plus an
`index.json` with the available dates) as part of the GitHub Actions
workflow. See
[`docs/deployment-github-actions-pages.md`](../docs/deployment-github-actions-pages.md)
for the full design of that part — this README only covers running and
trying out the site locally.
